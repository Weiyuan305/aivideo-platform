# AI 短剧制作平台：功能、创作者需求与当前产品差距

调研日期：2026-10-15。对象为制作工具，覆盖中文短剧/漫剧及通用叙事视频工作流，不涉及短剧播放平台或巴西市场。本文为研究建议，没有修改产品功能或开启模型 API。

**建议把下一阶段重心放在“按集、场景和镜头组织制作”，复用当前任务、worker、归档、声音库与工作流底座。** 现有平台解决了提交和执行管理；短剧创作者还需要决定每个镜头拍什么、用谁、选哪一版、如何接起来。两部分都必要，当前缺口主要在后者。

**证据与判断边界**

- 官方帮助文档能证明产品公开描述了某种操作；营销页面只能证明宣传了某种能力。本轮没有购买套餐或亲测竞争产品的生成质量。
- 社区原帖能提供实际问题、制作步骤和个案成本，不能代表全行业使用率。没有找到可信的跨平台功能调用占比，所以以下“高需求信号”不是用户比例或市场排名。
- Exa 共进行了 14 次查询，累计请求 79 条候选结果，返回文本包含 67 个不同候选 URL；另用网页搜索补查原帖并核读关键页面。被筛掉的内容包括聚合榜单、资源搬运、无关影视帖和明显宣传。候选网页数不等于有效研究样本量。
- X 证据较弱：部分内容来自搜索索引和公开转录，原帖打开返回 403。明确区分一手可读内容、转录和宣传，不把 X 的自动生成趋势摘要作为证据。
- “我们目前有/没有”根据本轮读取的 contracts、数据库 schema、实际模型目录投影、工作流端口和素材复用代码判断。没有以复制进仓库但未接入产品的上游组件名冒充可用功能，也没有重跑上轮测试或进行新一轮 UI 验收。

这组证据支持的结论是：**连续叙事制作的高频工作更可能集中在参考复用、镜头迭代、挑选和剪辑上。** 它不能证明某个网站的某个按钮使用量最高。教学机构 [Curious Refuge 的制作流程](https://curiousrefuge.com/blog/how-to-create-an-ai-film)也介绍角色设定、镜头表、分镜和多版本迭代；其课程销售属性需要一并考虑。

声音方面还要区分三件事：音色像谁、台词如何表演、人物嘴如何动。克隆接口只覆盖其中一部分。[Runway 多角色对白教程](https://help.runwayml.com/hc/en-us/articles/41748090660499-Creating-Multi-Character-Dialogues-with-Act-Two)明确需要分别准备角色表演素材并进行后续编辑，不能把“支持多人对白”理解成一次调用自动完成所有环节。

**已有功能需要调整哪些思路**

1. **让镜头成为主工作对象。** 用户进入某集，看到哪个镜头待分镜、待生成、待挑选或已采用。任务中心继续负责跨项目排队和故障排查；镜头卡内显示其任务进展，减少来回跳页。
2. **把文件库扩展为设定库。** 一个角色关联人脸、全身、多角度、服装版本与声音，一个场景关联多视角和道具关系。旧镜头引用固定设定版本；更新设定时提示受影响镜头，由人决定是否重做。参考能提高可控性，不能承诺消除所有漂移。
3. **区分故障重试与创作重拍。** 归档失败的重试不能再次产生推理费用；创作重拍则要新建候选，记录改动与预计费用。生成成功的结果仍可能不被采用。界面应支持并排看 A/B/C，选定 B 后仍保留其余版本。
4. **给工作流增加适合创作者的入口。** 普通路径是填写分镜和点具体动作；高级用户仍可编辑节点。故事板、素材画布和执行 DAG 分工不同，不宜把每张图都变成需要用户手连的技术节点。
5. **把语音克隆融入对白。** 保存“谁用什么声音”，再编辑“这一句怎么说、说多久、与哪个镜头对应”。情绪标签只是意图，服务商支持时才转换成参数；原生音视频生成与单独配音可以按镜头选用。
6. **先做可审核的批量，再考虑自主 Agent。** 先定角色/分镜，测试少量代表性镜头，再批量执行；AI 助手可以提议修改和估算影响，付费执行应受预算与用户设置约束。多 Agent 的名字本身不能改善失败率。

更进一步的“只改视频中的一小段”属于模型能力。[LTX Retake 官方说明](https://help.ltx.io/hc/en-us/articles/37060851452434-How-to-use-the-Retake-endpoint)确有这种 API；我们可以预留独立能力，但不能用普通任务重试假装已经实现视频局部修复。

**适合我们的一条制作链路**

```text
建立项目 / 一集
  → 导入或手工编辑剧本
  → 确认角色、服装、场景、声音设定
  → 编辑分镜：画面、台词、景别、运镜、时长
  → 生成或上传关键帧，审核并锁定
  → 生成镜头候选，比较并采用
  → 逐句配音 / 按需对口型
  → 排序、裁切、字幕和声音粗剪
  → 导出成片与素材包
```

第一阶段可从“2 个角色、1–2 个场景、6–12 个镜头、约 30–90 秒的一集”作为验收样本。这是我们的验证规模建议，不是行业标准。高级的多机位、3D 场景、自动审片等放在基础成片流程有真实用户后再验证。

**保持全 API 与轻量部署的实施顺序**

| 顺序 | 建议交付 | 无模型密钥也可完成的验收 |
| --- | --- | --- |
| 1 | 项目/集/场景/镜头结构，手工剧本与分镜，角色/场景/声音关联 | 上传自己的素材，创建一集，调整顺序，刷新后恢复；所有资源按账号隔离 |
| 2 | 镜头版本、采用版、参考用途、任务关联 | 用 fixture 或上传文件产生多个候选，替换采用版，确认已选结果不被后续任务覆盖 |
| 3 | 台词与剪辑结构、视频抽帧、基础粗剪和交付 | 用上传的视频/音频完成排序、裁切、字幕、预览、导出；无需生成模型 |
| 4 | 模型能力表、报价与预算、一个真实垂直链路 | 先用测试报价验证预算约束；真实质量、费用、口型与多参考效果必须等 API 接通后验收 |
| 5 | 选定镜头重做、上下游影响提示、少量内置配方 | 改一条台词只标记相关配音/口型/剪辑产物过期，保留可复用部分，不自动付费重跑 |

业务数据继续放 PostgreSQL；生成、抽帧、导出等复用统一任务与 CPU worker。剪辑结构可以先做普通元数据和浏览器预览；真正视频合成会增加 CPU/内存/磁盘工作量，需要设置分辨率、时长和并发限制。若要求服务端连这部分资源也尽量不承担，可把导出转给托管渲染 API；轻量部署不代表媒体渲染零资源。

没有理由为了这些业务层功能部署本地模型或 GPU，也没有必要先引入完整 ComfyUI 执行服务、Kubernetes 或新的队列系统。脚本智能拆解将来可调用语言模型 API；手工编辑和结构化导入应始终保留。

**优先级中暂时靠后的东西**

- 3D 导演台、精细动捕、任意 ComfyUI 节点、LoRA 训练：有价值，但与首期 API 轻量路线和基础闭环不匹配。
- 大型应用市场、创作者分成、公共作品社区：需要供给与运营，当前先验证用户能完成作品。
- 完整专业非线性编辑器：先覆盖粗剪，输出编号素材、SRT 和剪辑清单；若要输出剪映等专有工程格式，需要单独验证格式和版本兼容性。
- 全自动审美评分和无限自动重抽：容易把质量判断错误变成费用；先做人选、保留理由和有限次重做。

**怎样验证这些建议确实有用**

上线后按“项目与采用镜头”记录事件，避免仅用生成次数证明需求：

| 指标 | 建议定义 |
| --- | --- |
| 成片闭环率 | 有有效镜头的项目中，在观察期内至少成功导出一版成片的项目占比 |
| 到第一版成片的时间 | 首次建立有效分镜到首次成功导出的时间；结合活跃操作时长看，避免把离线等待混入 |
| 候选采用率 | 被采用过的候选数 / 成功生成的候选数；分图片、视频、声音统计 |
| 每个采用镜头成本 | 该镜头全部生成尝试实际费用 / 采用镜头数；不能只算最后一次 |
| 参考复用率 | 使用已有角色/场景/声音设定的镜头占比 |
| 返工原因 | 脸/衣服/场景不一致、动作错误、节奏、对白、口型等，由用户快速标记 |
| 局部修改节省 | 一次编辑实际重做的产物及费用，与全链重做估算比较；估算明确标注 |

以上指标目前都没有真实业务基线。第一轮可以邀请少量创作者做同一规模的样片，观察哪一步反复离开平台，优先补影响成片的步骤，再决定是否投入 Agent、团队协作或更复杂的画布。
